```
USER ─────────┐
  1           │ has many
              ▼
          DEVICE  (a physical browser/app install: "Rob's iPhone / Safari")

              │ issues many

              ├── refresh token  (long-lived, rotated, 1 active per session)
              └── access token   (5–15 min, stateless JWT or opaque)
```

**In one line each:**
- **Device** answers *where*. It's what the user sees in the "Your devices" list.
- **Session** answers *which login*. It's the unit you revoke.
- **Token** answers *what gets sent with this request*. Tokens are disposable, and revoking one shouldn't be how you revoke access.

## What revocation hits

```
 User action                     Server does                        Effect
 ─────────────────────────────────────────────────────────────────────────────
 "Sign out this device"   ──►  session.revoked_at = now()   ──►  refresh fails
                               (all sessions WHERE device_id=X)   access dies ≤ TTL
 "Sign out everywhere"    ──►  all sessions WHERE user_id=U  ──►  same, every device
 "Forget this device"     ──►  revoke sessions + delete device ─► next login = "new device"
 Password change          ──►  revoke all except current         (common default)
```

## Request-time check

```
request ──► access token valid & unexpired? ──no──► 401 → client uses refresh token
                    │yes
                    ▼
        need instant revocation? ──no──► ALLOW   (revocation lag = access TTL)
                    │yes
                    ▼
        session_id in revoked-cache? ──yes──► 401
                    │no
                    ▼
                  ALLOW

refresh ──► lookup session by refresh-token hash
              ├─ session revoked        → 401, client logs out
              ├─ token already rotated  → REUSE DETECTED → revoke whole session
              └─ ok → rotate: new refresh + new access (same session_id)
```

## Minimal schema

```
devices   (id, user_id, label, user_agent, first_seen, last_seen)
sessions  (id, user_id, device_id, created_at, last_used_at,
           revoked_at, revoked_reason, ip, auth_method)
refresh_tokens (id, session_id, token_hash, issued_at, replaced_by, expires_at)
```

The access token carries `sub=user_id` and `sid=session_id`, and nothing else is stateful.

## Decisions you need to make

1. **Is a device a real table or just a label on the session?** If users only ever see "active sessions", you can skip the `devices` table and store the UA and IP on the session. Add the table when you want device-level trust, like "remember this device, skip MFA".
2. **How fast must revocation take effect?** You can wait out the access-token TTL, which is simple and gives a 5–15 min lag. Or you can check a revoked-`sid` denylist on every request (Redis, with entries expiring after the access TTL), which is instant but costs a lookup per request. My recommendation is to start with a short TTL and add the denylist only if the lag matters.
3. **Should "sign out everywhere" keep the current session?** It usually should.

## The four things, and how they nest

```
 User ─────────── who you are
  │ 1
  │
  │ *
 Device ───────── where you're logged in from (a laptop's Chrome, the iOS app on a phone)
  │ 1              label + grouping. NOT a security boundary.
  │
  │ *   (usually just 1 active at a time)
 Session ──────── one login. This is the thing you revoke.
  │ 1              starts at login, ends at logout / revoke / expiry
  │
  │ *
 Refresh token ── the long-lived credential that proves the session is still alive
  │                rotated on every use; the whole chain is one "family"
  │ mints
  ▼
 Access token ─── short-lived (5–15 min), stateless, carries `sid` (the session ID)
                   never revoked one by one; it just expires
```

**The main idea:** tokens are credentials, sessions are state, and devices are labels. You revoke state. Tokens stop working because the state behind them is gone.

## What each one holds

| Entity | Key fields | Lives where | Lifetime |
|---|---|---|---|
| **Device** | `id`, `user_id`, `name` ("Rob's MacBook"), `platform`, `user_agent`, `first_seen`, `last_seen` | DB, plus a device ID stored on the client (cookie or keychain) | Until the user removes it |
| **Session** | `id`, `user_id`, `device_id`, `created_at`, `last_used_at`, `expires_at`, `revoked_at`, `ip` | DB | Days to weeks |
| **Refresh token** | `hash`, `session_id`, `parent_hash`, `used_at` | DB (hashed only) | Until rotated |
| **Access token** | `sub`, `sid`, `exp` | Client only (JWT) | Minutes |

## What the revoke operations do

```
"Sign out this device"   → UPDATE sessions SET revoked_at=now() WHERE device_id=?
"Sign out this session"  → UPDATE sessions SET revoked_at=now() WHERE id=?
"Sign out everywhere"    → UPDATE sessions SET revoked_at=now() WHERE user_id=?
"Sign out all but this"  → ... WHERE user_id=? AND id != current_sid
Password change          → sign out everywhere (optionally keep the current session)
Refresh token reused     → revoke that session (a reused token probably means it was stolen)
```

## After a revoke, when does the device actually get kicked out?

```
revoke ──► next refresh attempt fails ──► client logged out
             ▲
             └─ gap = remaining access token TTL (up to 15 min)
```

Two ways to handle that gap. I'd start with the first:

1. **Accept the gap.** Keep access tokens short (5–10 min). No per-request DB check. This is how most apps work.
2. **Close the gap.** Keep a `revoked_sid` set in Redis with a TTL equal to the access token TTL, and check it on each request. This is cheap. Add it only if "revoke" has to mean "right now" (admin kill switch, compliance).

## Should Device be its own table?

This is the question most likely behind the mushiness. Here's how to decide:

- **Merge Device into Session** (just put `device_name`, `user_agent` and `platform` on the session row) if all you need is a "your active sessions" list with revoke buttons. Each login is one row. It's simpler, and it's what GitHub-style session lists show.
- **Keep Device separate** if something about a device has to outlast a single login:
  - "Trust this device, skip 2FA for 30 days"
  - Push notification tokens
  - "New device sign-in" alerts, which need to know you've seen this device before
  - Blocking one device permanently

**My recommendation:** start with sessions only, with the device fields stored on the session row. Add a `devices` table when one of the features above actually shows up. The migration is easy: group existing sessions by a client-generated device ID.

## Suggested build order

1. `sessions` table. Every login creates a row. Access tokens carry `sid`.
2. Refresh token rotation with a `session_id` foreign key, plus reuse detection.
3. `GET /sessions` and `DELETE /sessions/:id` endpoints, and a "sign out all others" action.
4. Settings UI: list sessions with device name, location and last active time, and a revoke button on each.
5. Optional: the Redis `revoked_sid` check for immediate revocation.
6. Optional: a `devices` table once trusted-device or push features need it.

## 1. What each thing is

```
User ──1:N──▶ Device ──1:N──▶ Session ──1:N──▶ Refresh token (rotating) ──1:N──▶ Access token
               (hardware)      (one login)       (stored in DB)                     (stateless, ~5–15 min)
```

| Concept | What it really is | Stored? | Lifetime | Can you revoke it? |
|---|---|---|---|---|
| **Device** | A label for a physical client ("Rob's iPhone") | Optional | Indefinite | Only by revoking the sessions under it |
| **Session** | One successful login on one client | **Yes (this is the key row)** | Days to months | **Yes. Revocation happens here.** |
| **Refresh token** | Proof you hold that session; swapped for a new one on every use | Yes, hashed, linked to a session | Until used or expired | Revoked with its session |
| **Access token** | Short-lived bearer credential (e.g. a JWT) | No | Minutes | No. It just expires. |

**The core idea:** a session is the thing that gets revoked. Tokens are credentials that belong to a session. A device is just a way to group sessions for display.

## 2. How revocation plays out

```
 User clicks "Sign out of iPhone"
            │
            ▼
 UPDATE sessions SET revoked_at = now() WHERE id = :sid AND user_id = :uid
            │
            ├──▶ Refresh token: the next /refresh call finds the session revoked → 401 → client logs out
            │
            └──▶ Access token still in flight: either
                   (a) let it expire (≤ TTL, simple), or
                   (b) put the sid claim in the JWT and check it against a revoked-sessions
                       cache (Redis set with TTL = access TTL) → immediate cutoff
```

"Sign out everywhere" is the same query without the `id` filter. "Sign out everywhere except here" adds `AND id != :current_sid`.

## 3. The minimal schema

```
sessions
  id              uuid  PK            ← goes into the access token as the `sid` claim
  user_id         FK
  device_label    text                ← "Chrome on macOS" (parsed from user-agent, user can rename)
  created_at, last_seen_at, last_ip
  revoked_at      timestamp NULL

refresh_tokens
  token_hash      PK
  session_id      FK → sessions
  replaced_by     NULL | token_hash   ← rotation chain
  expires_at
```

**Reuse detection:** if a refresh token comes in that was already replaced, someone stole it. Revoke the whole session.

## 4. Do you need a separate `devices` table?

**Probably not yet.** In most apps, one device holds one active session, so a label on the session row covers it. Add a real `devices` table only if you need something that has to outlive a login:
- "Trusted device, skip MFA"
- Push notification tokens
- A persistent device name or ID across logouts and re-logins

If you add it later, `sessions.device_id` becomes a foreign key, and "revoke device" means revoking all of that device's sessions. The session is still the thing you revoke.

## 5. Decisions to make before planning the work

1. **Access token TTL and whether you need instant cutoff.** This picks option (a) or (b) above. Option (b) adds a lookup on every request.
2. **Where the refresh token lives on web:** httpOnly cookie or app storage. This decides how `/refresh` authenticates.
3. **What counts as "the current session"** in the UI, so users can't accidentally revoke themselves, or can do so on purpose.
4. **Whether a password change or MFA reset revokes all sessions.** Usually yes, except the current one.
